الخلاصة بالعربي

صار الموظّف يقدر ياخد أكثر من دور عند نفس العميل — مثلاً مصمّم وكاتب محتوى بنفس الوقت. الحقل الجديد اسمه roles وهو مصفوفة، والقديم role ما زال شغّال ومساوي دائماً لأول عنصر.

ما في شي بينكسر. الشاشات الحالية بتضل تشتغل زي ما هي. الشغل المطلوب: تحويل قائمة اختيار الدور إلى اختيار متعدّد، وعرض roles بدل role.

⚠️ أهم نقطة: roles بتستبدل القائمة كلها — إذا بدك تضيف دور، ابعت الأدوار القديمة + الجديد مع بعض.

1What changed, in one picture

Before

One membership, one role. Ahmad was either the Designer on Taxero or the Copywriter — never both.

{
  "id": "uuid",
  "userId": "uuid",
  "companyId": "uuid",
  "role": "DESIGNER",
  "status": "ACTIVE"
}

After

One membership, a list of roles. Both fields come back; role is always roles[0].

{
  "id": "uuid",
  "userId": "uuid",
  "companyId": "uuid",
  "roles": ["DESIGNER", "COPYWRITER"],
  "role": "DESIGNER",
  "status": "ACTIVE"
}

Still one membership row per person per client — the roles moved inside it. A person does not appear twice in a member list, and the client switcher is untouched.

2What you must not miss

roles replaces the whole set

PATCH is not "add a role" — it is "these are now their roles". Sending {"roles":["ACCOUNT_MANAGER"]} for somebody who was ["DESIGNER","COPYWRITER"] leaves them holding only Account Manager. To add a hat, send the existing list plus the new one.

Nothing you have today breaks

Screens still sending {"role":"DESIGNER"} keep working and get roles:["DESIGNER"] back. You can ship the multi-select whenever it suits you — there is no deadline and no coordinated release.

Send one or the other

Send roles or role, never both in the same body. If both arrive, roles wins — but do not rely on that, it is an accident of the implementation rather than a promise.

3The endpoints

POST/api/companies/:companyId/memberslive

Who: Admin, Super Admin · Put an employee on a client

Request

{
  "userId": "uuid",
  "roles": ["DESIGNER", "COPYWRITER"]     // one or more
}

// still accepted, treated as a one-item list:
{ "userId": "uuid", "role": "DESIGNER" }

201 Response

{
  "id": "uuid",
  "companyId": "uuid",
  "userId": "uuid",
  "roles": ["DESIGNER", "COPYWRITER"],
  "role": "DESIGNER",
  "status": "ACTIVE",
  "invitedById": "uuid",
  "createdAt": "...", "updatedAt": "..."
}
  • Duplicates in the list are removed server-side — ["DESIGNER","DESIGNER"] is stored as one.
  • Order is preserved, and role becomes the first entry. Put the person's main hat first if that label matters in your UI.
  • Adding somebody who is already active on the client is a 409. Filter existing members out of the picker.
  • Adding somebody who was removed before reactivates their old membership with the new roles, keeping their history rather than starting a second record.

PATCH/api/companies/:companyId/members/:membershipIdlive

Who: Admin, Super Admin · Change what somebody does on a client

{ "roles": ["COPYWRITER", "DESIGNER", "SOCIAL_MEDIA_MANAGER"] }

// also accepts, as before:
{ "role": "COPYWRITER" }
{ "status": "SUSPENDED" }        // ACTIVE | INVITED | SUSPENDED

// 200 → the full updated membership, both fields present

Remember: the list you send is the list they end up with.

GET/api/companies/:companyId/memberslive

Who: Account Manager on that client, or any admin · The members table

[
  {
    "id": "uuid",
    "userId": "uuid",
    "roles": ["DESIGNER", "COPYWRITER"],
    "role": "DESIGNER",
    "status": "ACTIVE",
    "user": { "id": "uuid", "fullName": "Ahmad", "email": "ahmad@..." },
    "createdAt": "...", "updatedAt": "..."
  }

Newest first. Includes non-active memberships, so filter on status === 'ACTIVE' for "who works here now".

GET/api/userslive

Who: Admin, Super Admin · The employees screen

Each employee carries the clients they work on, and each of those now carries roles:

{
  "id": "uuid", "fullName": "Ahmad", "email": "ahmad@solutions.local",
  "platformRole": "USER", "status": "ACTIVE",
  "clients": [
    { "membershipId": "uuid", "companyId": "uuid", "companyName": "Taxero",
      "roles": ["DESIGNER", "COPYWRITER"],   // ← render this
      "role": "DESIGNER" }                   // ← deprecated
  ]
}

DELETE/api/companies/:companyId/members/:membershipIdlive

Who: Admin, Super Admin · Take somebody off a client

Unchanged, and still the right way to remove a person. Do not try to express "no longer works here" by sending an empty roles array — that is rejected. Deactivating keeps their history and lets them be re-added later.

5How permissions behave now

Three properties worth knowing, because they change what your UI can assume:

  • Any role wins. A check passes if at least one held role allows the action. Ahmad as ["DESIGNER","ACCOUNT_MANAGER"] can do everything a Designer can and everything an Account Manager can.
  • Read fresh on every request. Company roles are not in the JWT. Give somebody a new role and it works on their very next click — no logout, no token refresh. Verified: a Designer got 403 on an Account-Manager route, was given the extra role, and the same token got 200.
  • Platform role is separate. platformRole (SUPER_ADMIN / AGENCY_ADMIN / USER) is one value per person and is not a list. Only the per-client roles are multiple.

One consequence for the UI

If your interface hides or shows things based on "the user's role on this client", it must now check membership in a list, not equality with one value. role === 'DESIGNER' silently becomes wrong the day somebody gets a second hat.

if (member.role === 'DESIGNER')            // wrong — only sees the first hat
if (member.roles.includes('DESIGNER'))     // right

سلوك الصلاحيات

الصلاحية بتمرّ إذا أي دور من أدواره بيسمح بالعملية. والأدوار بتنقرأ مع كل طلب — يعني لما تعطي حدا دور جديد بيشتغل فوراً بدون ما يعمل تسجيل خروج ودخول.

Render the roles as pills so two hats read as clearly as one:

DesignerCopywriter   Account Manager

Rules for the multi-select

  • Pre-tick the roles the person already holds — the form starts from their current set, because saving replaces it.
  • Disable Save when nothing is ticked, rather than letting the 400 teach the user the rule.
  • Show the client-side roles (CLIENT_OWNER, CLIENT_REVIEWER) separately, or hide them for employees — mixing "our staff" and "their people" in one list confuses whoever is assigning.

7Recipes

// types
export type MembershipRole =
  | 'ACCOUNT_MANAGER' | 'COPYWRITER' | 'DESIGNER' | 'SOCIAL_MEDIA_MANAGER'
  | 'CLIENT_OWNER' | 'CLIENT_REVIEWER' | 'SALES_AGENT';

export type Membership = {
  id: string;
  companyId: string;
  userId: string;
  roles: MembershipRole[];        // read this
  role: MembershipRole;           // deprecated — always roles[0]
  status: 'ACTIVE' | 'INVITED' | 'SUSPENDED';
  user?: { id: string; fullName: string; email: string };
};

Add a person with two hats

await api.post(`/companies/${clientId}/members`, {
  userId,
  roles: ['DESIGNER', 'COPYWRITER'],
});

Give an existing member one more hat

// send the whole set — the existing roles plus the new one
await api.patch(`/companies/${clientId}/members/${m.id}`, {
  roles: [...m.roles, 'ACCOUNT_MANAGER'],
});

Take one hat away, keep the rest

const next = m.roles.filter((r) => r !== 'COPYWRITER');

if (next.length === 0) {
  // the last role cannot be removed — this means "remove the person"
  await api.delete(`/companies/${clientId}/members/${m.id}`);
} else {
  await api.patch(`/companies/${clientId}/members/${m.id}`, { roles: next });
}

Save straight from the multi-select

const selected = form.roles;              // MembershipRole[]

if (selected.length === 0) return setError('Pick at least one role');

await api.patch(`/companies/${clientId}/members/${m.id}`, { roles: selected });
invalidate(['members', clientId]);        // and the employees list

Build the picker without duplicates

const employees = await api.get('/users');
const members   = await api.get(`/companies/${clientId}/members`);

const assignable = employees.filter(
  (e) => !members.some((m) => m.userId === e.id && m.status === 'ACTIVE'),
);

Rollout

There is no coordinated release. The backend accepts both shapes today, so items 1–2 can ship on their own, and the multi-select can follow whenever it reaches the top of the list. The single role field will only be removed once you confirm nothing sends or reads it.

خطة التنفيذ

ما في إصدار متزامن ولا موعد نهائي. الباك إند بيقبل الشكلين. ابدأ بالنقطتين ١ و٢ (النوع، وincludes بدل ===)، وبعدين الاختيار المتعدّد وقت ما يجي دوره. حقل role القديم رح ينشال بس تأكّدوا إنه ما حدا بيستعمله.
