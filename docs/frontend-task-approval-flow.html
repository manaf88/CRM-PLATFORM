Task Approval Flow

A task now carries a named approver. The person doing the work submits it for review, the approver approves it or sends it back with a note, and every step is recorded. IN_REVIEW stops being a label anybody can set and becomes a queue somebody owns.

One breaking change — read this first

Any status control that offers IN_REVIEW will now fail with 409. The status endpoint can no longer move a task into or out of review. That control becomes a Submit for review button, and the approver gets Approve / Request changes. Everything else in this document is additive.

1What changed, in one picture

Before

One person on the task. Anybody with a work role could set any status, including IN_REVIEW.

PATCH /tasks/:id/status
{ "status": "IN_REVIEW" }   // who is it waiting on? nobody knows

// approval lived in the comments,
// so nothing recorded that Omar said yes

After

Two people on the task: the assignee does the work, the approver says yes. Three actions own the review.

POST /tasks/:id/submit-for-review   // assignee
POST /tasks/:id/approve             // approver
POST /tasks/:id/request-changes     // approver + note

// "Approved by Omar at 14:20" is now a real row

The row itself never changes hands. assignedToId stays on the person who did the work through the whole review, which is what keeps "who wrote this" answerable after three rounds of changes.

The flow it implements

StepWhoWhat the UI does
Write the copyJessika · assigneeSubmit for review → status becomes IN_REVIEW
Gate 1Account manager · approverTask appears in their approval queue → Approve or Request changes
DesignYasin · assignee of the next taskSame submit button on their own task
Gate 2Omar · approverSame queue, same two buttons

Stage hand-off is not automatic yet

This release is one approver per task. Moving from the copy task to the design task is done by creating the next task, the same way you do today. Automatic chaining on a post (sequence, blocking stage 2 until stage 1 is approved, pushing the post to READY_FOR_CLIENT) is a separate ticket.

The five new fields
FieldTypeWhat it means for the UI
approverIduuid · nullableWho must say yes. Null means the task cannot be submitted — show "needs an approver" and let the user pick one.
approverobject · nullable{ id, fullName, email, status }. Use status !== "ACTIVE" to flag an approver who has been deactivated.
submittedForReviewAtISO date · nullableWhen it was handed over. This is what you age — "waiting 2 days". Cleared on approve, request-changes and cancel.
reviewedAtISO date · nullableThe last verdict, approve or request-changes.
reviewNotestring · nullableThe approver's last note. Show it at the top of the task while the doer is reworking it. Full history is in the activity log.

There is no new status. IN_REVIEW already existed; it now has an owner.

3The three review actions

All paths are prefixed with /api and need the usual Authorization: Bearer <token>. Each action returns 200 with the full task object above.

POST/api/companies/:companyId/tasks/:taskId/submit-for-reviewnew

Who: the assignee, or Admin / Super Admin · No body

// 200 → the task, now IN_REVIEW with submittedForReviewAt set.
// The approver gets a notification.

// 422 — the task has nobody to approve it
{ "statusCode": 422, "error": "Unprocessable Entity",
  "code": "APPROVER_REQUIRED",
  "message": "This task has no approver. Set one before submitting it for review." }

// 409 — wrong status (only TODO and IN_PROGRESS can be submitted)
{ "statusCode": 409, "error": "Conflict",
  "code": "INVALID_TRANSITION",
  "message": "A task in DONE cannot take the action submit-for-review",
  "from": "DONE", "action": "submit-for-review" }

// 403 — somebody other than the assignee pressed it
{ "statusCode": 403, "error": "Forbidden",
  "message": "Only the person this task is assigned to can submit it for review" }

POST/api/companies/:companyId/tasks/:taskId/approvenew

Who: the approver, or Admin / Super Admin · No body

// 200 → status DONE, reviewedAt and completedAt set,
// submittedForReviewAt back to null. The assignee is notified.

// 409 — the task is not in review (somebody else already decided)
{ "statusCode": 409, "error": "Conflict", "code": "INVALID_TRANSITION",
  "message": "A task in IN_PROGRESS cannot take the action approve",
  "from": "IN_PROGRESS", "action": "approve" }

// 403 — not the approver
{ "statusCode": 403, "error": "Forbidden",
  "message": "Only the approver of this task can approve it" }

Two approvers pressing at the same moment is handled: the first wins, the second gets the 409 above. Refresh the task on 409 rather than retrying.

POST/api/companies/:companyId/tasks/:taskId/request-changesnew

Who: the approver, or Admin / Super Admin · Note required

// request
{ "note": "Tighten the headline and swap the second slide" }

// 200 → status back to IN_PROGRESS, same assignee, reviewNote stored,
// submittedForReviewAt cleared. The assignee is notified with the note.

// 422 — empty or whitespace-only note
{ "statusCode": 422, "error": "Unprocessable Entity",
  "code": "REVIEW_NOTE_REQUIRED",
  "message": "Say what needs changing: a note is required." }

It goes back one step, to the same person — never to the start of the chain. Re-submitting sends it to the same approver unless somebody deliberately changes approverId.

4The approval queue

GET/api/companies/:companyId/tasks/approval-queuenew

Who: any internal member (not client users) · ?limit=25&offset=0

// Tasks where status = IN_REVIEW and approverId = the caller.
// Oldest submission first — the top row is the one keeping people waiting.
{
  "items": [ { …the task object… } ],
  "total": 7,
  "limit": 25,
  "offset": 0
}

Paginated exactly like GET /tasks/my. Age each row from submittedForReviewAt.

The queue is per client

The path is scoped to one companyId, so somebody who approves on several clients has several queues. A single cross-client queue is not built — if the team wants "everything waiting on me" in one screen, say so and we will add it as its own endpoint rather than have the frontend fan out over every client.

5Where the approver comes from

You normally do not type a name. When a task is created without approverId, the backend reads the responsibility matrix: the task type maps to an area of work, and whoever holds TO_APPROVE in that area for that client becomes the approver. Exactly one active person wins. Zero or several leaves the task with approverId: null — the create still succeeds, and the UI asks for a name.

GET/api/companies/:companyId/tasks/resolve-approver?taskType=DESIGNnew

Who: Account Manager, Social Media Manager, or any admin · Pre-fills the approver picker

{
  "taskType": "DESIGN",
  "approverId": "4c93…",        // null unless exactly one active approver
  "reason": "RESOLVED",
  "areaId": "7f21…",
  "areaName": "Design",
  "candidateUserIds": ["4c93…"] // everybody holding TO_APPROVE there
}
reason — what the picker should say
reasonMeaning · suggested UI
RESOLVEDOne approver. Pre-select them, still editable.
MULTIPLE_APPROVERSSeveral people approve this area. Show candidateUserIds as the choices — "who approves this one?"
NO_APPROVER_IN_AREAThe area exists but nobody active holds TO_APPROVE. Offer the full member list, and a link to the matrix screen.
NO_MATCHING_AREAThis client has no area for that kind of work. Same fallback, and worth nudging an admin to set the area key (section 8).
UNMAPPED_TASK_TYPEGENERAL tasks have no area by design. Ask for the approver, or leave it empty.

POST/api/companies/:companyId/taskschanged

Who: Account Manager, Social Media Manager, or any admin · approverId is new and optional

{
  "title": "Taxero — May carousel",
  "taskType": "DESIGN",
  "assignedToId": "8a10…",
  "approverId": "4c93…"     // optional — omit it and the matrix decides
}

// 201 → the full task, with assignedTo and approver filled in.
// 422 if the approver is not an active member of this client:
{ "statusCode": 422, "error": "Unprocessable Entity",
  "code": "APPROVER_REQUIRED",
  "message": "The approver must be an active member of this company" }

The matrix is read once, at creation

Changing the matrix later never rewrites tasks that already exist — a task that was waiting on Omar keeps waiting on Omar. To move a waiting task to somebody else, send PATCH /api/companies/:companyId/tasks/:taskId with { "approverId": "…" }. That is the "Omar is on holiday" button, it is open to the Account Manager and admins, and it writes a TASK_APPROVER_CHANGED row to the activity log.

6The status endpoint is now fenced

PATCH/api/companies/:companyId/tasks/:taskId/statuschanged

Who: unchanged · IN_REVIEW is no longer a value you may send

// 409 — trying to enter review through the back door
{ "statusCode": 409, "error": "Conflict",
  "code": "REVIEW_ACTIONS_ONLY",
  "message": "IN_REVIEW is managed by the review actions. Use submit-for-review, approve or request-changes.",
  "from": "IN_PROGRESS", "to": "IN_REVIEW",
  "actions": ["submit-for-review", "approve", "request-changes"] }

// 409 too — trying to leave review without a verdict
{ …same code, "from": "IN_REVIEW", "to": "DONE" }

// still allowed: cancelling a task that is in review
{ "status": "CANCELED" }   // → 200, and the waiting clock is cleared

Practically: remove IN_REVIEW from every status dropdown. A task in review shows its status as read-only, with the two approver buttons for the approver and a "waiting on name" line for everybody else.

8Responsibility areas gain a key

Areas are free text and differ per client — "Design" on one, "Creative" on the next, «تصميم» on the third — so matching a task type to an area by name alone would silently find nothing. Each area now has an optional areaKey, and that is what the matching actually runs on.

POST/api/companies/:companyId/responsibility-areaschanged

Also on PATCH …/:areaId · Returned on every area response

{
  "name": "تصميم",
  "areaKey": "DESIGN"     // NEW — optional, stored upper-cased, unique per client
}

// 409 if another area on this client already uses that key

A small select next to the area name is enough. Without a key the backend falls back to a list of known names in English and Arabic, which works for the common spellings but not for a client who invented their own. This one field is what makes "Omar is on holiday — change one cell instead of forty tasks" actually work.

Error handling, once, in the API layer

The approval endpoints return a code in the body alongside message. Switch on the code, not the message text: APPROVER_REQUIRED and REVIEW_NOTE_REQUIRED (422), INVALID_TRANSITION and REVIEW_ACTIONS_ONLY (409). On any 409 the right move is to refresh the task — it means somebody else already acted.

11Not in this release

  • Chained tasks on a post. sequence, blocking a stage until the previous one is approved, and moving the post to READY_FOR_CLIENT when the last gate passes. Separate ticket — the post flow needs two decisions from product first.
  • A cross-client approval queue. Today the queue is per client.
  • Email digests for ageing approvals.
  • Swagger. The API has no OpenAPI setup at all yet, so this document is the contract. Tell me if anything here does not match what you see and I will fix the backend, not the document.
