Read this first

Two roles now reach the dashboard: Admin (AGENCY_ADMIN) and Super Admin (SUPER_ADMIN). Admin can add a client, edit a client name and assign a client to users. Only Super Admin can assign admins and delete a client from the database.

Every endpoint below carries a status chip. live exists in the API today and you can call it now. spec is the agreed contract, not built yet — build the UI against it, but expect 404 until the backend ships it. fix exists but its permission rule is changing, so behaviour will tighten.

1What changed

The operations dashboard was specified as Super-Admin-only. It is now open to both administrator roles, and the client administration actions around it have been split between them.

Change log — revision 2 of the backend task list
#ChangeWhat the frontend does about it
1 Admin now reaches the dashboard. All of /api/admin/dashboard/* accepts AGENCY_ADMIN as well as SUPER_ADMIN. Show the dashboard entry point for both roles. Do not hide it behind a Super Admin check.
2 Both roles see the whole agency. Admin is not narrowed to the clients they are a member of. No "my clients only" toggle on the dashboard. The client filter is a convenience, not a permission.
3 Admin can add a client, rename it, and assign it to users. Enable those three actions for both roles.
4 Assigning admins is Super Admin only. A new dedicated route replaces role changes through the general user update. Show the role control only to Super Admin. Stop sending platformRole to PATCH /api/users/:userId.
5 Deleting a client is Super Admin only and is a permanent database delete, separate from archiving. Two distinct actions in the UI: "Archive" (status change, both roles) and "Delete permanently" (Super Admin, typed confirmation).
6 Renaming a client tightens. Today any member of a client can rename it; it will require an admin role. Remove the rename control from non-admin client screens now, so it does not start failing with 403 later.
7 System health stays Super Admin only. Render that widget for Super Admin only. Open question — may widen to Admin.
8 A person can hold several roles on one client. Memberships carry a roles list; the old single role still works and mirrors the first entry. Turn the role dropdown in "Assign people" into a multi-select, and render roles wherever a role is shown today.

Nothing else moved

Authentication, the client workspace, tasks, posts, approvals, leads and campaigns keep the same routes and shapes. This document only adds the admin area and the client-administration rules around it.

// One helper, used everywhere — do not scatter role string comparisons
export const isAdmin = (r?: PlatformRole) =>
  r === 'SUPER_ADMIN' || r === 'AGENCY_ADMIN';

export const isSuperAdmin = (r?: PlatformRole) => r === 'SUPER_ADMIN';

// Route guard

// Destructive controls
{isSuperAdmin(user.platformRole) && <DeleteClientButton clientId={id} />}

Hiding a button is not a permission

Role checks in the frontend are cosmetic — the API enforces the real rule and returns 403. Never treat a hidden control as security, and always handle a 403 gracefully: it means the role changed under the user (see Flow 7), not that something is broken.

3Conventions

Authentication

  • Send Authorization: Bearer <accessToken> on every admin request.
  • The refresh token is an httpOnly cookie, so every call must use credentials: 'include'. Your origin has to be in the API's allow-list or the browser blocks it.
  • On 401, call POST /api/auth/refresh once and retry. On a second 401, sign out.

Error responses

StatusMeansWhat the UI should do
400Validation — bad date, bad UUID, unknown body fieldShow the field error. Never retry unchanged
401Missing or expired access tokenRefresh once, then retry; otherwise sign out
403Role not allowed for this actionRe-read the role, hide the control, tell the user their access changed
404Record not found — or endpoint not built yetFor spec endpoints treat it as "not shipped" and render the widget's empty state
409Conflict — the delete confirmation did not matchKeep the modal open and explain the mismatch

Unknown body fields are rejected

The API validates with whitelist and forbidNonWhitelisted. An extra property in a request body is a 400, not a silently ignored field. Send exactly the documented keys — this is the most common integration mistake.

4Endpoints that already exist and behave differently

GET/api/companieslive

Who: any signed-in user — but the result depends on the role

For SUPER_ADMIN and AGENCY_ADMIN this already returns every client in the database, newest first. For an employee it returns only the clients they are assigned to.

Use it to populate the dashboard's client filter dropdown — you do not need a separate admin endpoint for the client list. Cache it per session; it changes only when a client is added or deleted.

PATCH/api/users/:userIdbreaking

Who: Admin, Super Admin

General employee update — name, status, password reset. platformRole is being removed from this body. Because unknown fields are rejected, sending it after the change is a 400, not a no-op.

Move every role change to PATCH /api/users/:userId/platform-role (§6). Split your employee-edit form: name/status/password here, role in a separate Super-Admin-only control.

5New API — dashboard reads

All twelve are GET, all accept the §3 filters, all are open to Admin and Super Admin, and none require a client to be selected first. They are independent on purpose: each widget fetches its own endpoint so one slow query cannot block the page.

Who: Admin, Super Admin · Filters: all · Cheap — poll this one

How the frontend uses it: the KPI row at the top of the dashboard. Nine numbers, one request. Refresh on mount, on filter change, and every 60 s while the tab is visible. Each tile links to the matching drill-down screen.

6New API — client administration writes

POST/api/companieslive

Who: Admin, Super Admin · This is "add client"

Body — name is the only required field; everything else is optional and can be filled in later from the client's settings screen.

{
  "name": "Taxero",                      // required, 2–160 chars
  "industry": "Accounting",              // optional, ≤120
  "website": "https://taxero.com",       // optional — MUST include https://
  "phone": "+962790000000",              // optional, ≤40
  "city": "Amman",                       // optional, ≤120
  "country": "Jordan"                    // optional, ≤120
}

// 201 → the created client
{ "id": "uuid", "name": "Taxero", "status": "ACTIVE",
  "createdById": "uuid", "createdAt": "...", "updatedAt": "..." }

How the frontend uses it: a short "New client" dialog with one required field. Two things to know:

  • website without a protocol is a 400. Prefix https:// for the user, or validate before sending.
  • The creator is automatically added to the new client as ACCOUNT_MANAGER. Do not also call the members endpoint for them — you would get a duplicate-membership error. Refresh your client list afterwards, then send the user to the assign-members step (Flow 3).

POST/api/companies/:companyId/memberslive

Who: Admin, Super Admin · This is "assign client to users"

Body — an existing employee's id plus one or more roles they hold on this client. Somebody can be the Designer and the Copywriter on the same client, and hold a different set again on another client.

{
  "userId": "uuid",
  "roles": ["DESIGNER", "COPYWRITER"]
}

// roles — any combination of:
// ACCOUNT_MANAGER | COPYWRITER | DESIGNER | SOCIAL_MEDIA_MANAGER
// CLIENT_OWNER | CLIENT_REVIEWER | SALES_AGENT

// 201 → the membership
{ "id": "uuid", "companyId": "uuid", "userId": "uuid",
  "roles": ["DESIGNER", "COPYWRITER"],   // every hat they wear
  "role": "DESIGNER",                    // the first one, for older callers
  "status": "ACTIVE", "invitedById": "uuid",
  "createdAt": "...", "updatedAt": "..." }

Companion routes

GET    /api/companies/:companyId/members                  // list, for the table
PATCH  /api/companies/:companyId/members/:membershipId    // { "roles": ["COPYWRITER","DESIGNER"] }
DELETE /api/companies/:companyId/members/:membershipId    // deactivates the membership

How the frontend uses it: an "Assign people" panel on the client — a table of current members from GET, an employee picker fed by GET /api/users, and a multi-select of roles. Notes:

  • roles replaces the whole set. To add a hat, send the existing roles plus the new one — a PATCH carrying one role leaves that person holding exactly that one.
  • An empty roles array is a 400. Somebody on a client with no role would have no permissions at all, so that state is not allowed to exist; remove them with DELETE instead.
  • The single role field is still accepted on POST and PATCH and is treated as a one-item list, so existing screens keep working untouched. Send roles or role, not both.
  • Every response carries both: roles (the full list) and role (its first entry). Render roles; treat role as deprecated.
  • A permission check passes if any held role allows the action, and roles are read per request — a new role takes effect immediately, with no re-login.
  • The employee must already exist. There is no self-sign-up: create them with POST /api/users first.
  • One membership per person per client is still enforced by the database — the roles live on that one membership. Filter people who are already members out of the picker.
  • DELETE deactivates rather than erases, so the person disappears from the client but their history stays intact.
  • The permission on PATCH and DELETE is tightening to admin-only alongside POST — keep all three controls in the admin area only.

The role lives in the token

A role change does not reach an already–signed-in user until their token is re-issued. If you change your own team's roles while they are working, expect a short window where their UI still shows the old capabilities and the API answers 403. That is exactly what Flow 7 handles.

409confirm does not match the nameKeep the modal open, mark the input invalid
404Already deletedTreat as success, refresh the list

How the frontend uses it: the most dangerous control in the product. Build it as a deliberate, slow path:

  • Put it in a "Danger zone" block at the bottom of the client settings screen, visually separated from Archive.
  • Require the user to type the client name to enable the confirm button; send that exact string as confirm.
  • State the consequence in the dialog using real numbers — fetch the client's row from /dashboard/clients and show the tasks, posts and leads that will be destroyed.
  • Afterwards: clear that client from every cache, drop it from the client switcher, and if the user was inside its workspace, redirect to the dashboard. Report the removed counts in the success toast.
  • Archive is not this. For a client that is merely finished, use PATCH with {"status": "ARCHIVED"} — available to Admin, and reversible.

8How to use it — the seven flows

1

Render the dashboard for either admin role

Read platformRole from the session. If it is not one of the two admin roles, redirect away — do not fetch. Otherwise fire the widget requests in parallel and let each resolve on its own.

const f = { from: today, to: today };            // defaults = today
const [overview, attention, tasks] = await Promise.allSettled([
  api.get(`/admin/dashboard/overview?${qs(f)}`),
  api.get(`/admin/dashboard/attention?${qs({ ...f, page: 1, limit: 20 })}`),
  api.get(`/admin/dashboard/tasks?${qs(f)}`),
]);
// allSettled, not all — one failed widget must not blank the page
2

Filter the whole dashboard to one client

Add clientId to the shared filter object and refetch every visible widget. No workspace switch, no page reload, and no permission question — both admin roles may filter to any client.

setFilters(f => ({ ...f, clientId }));   // → all widgets refetch
router.replace(`/admin/dashboard?${qs({ ...filters, clientId })}`);
3

Add a client, then staff it

Two requests, one wizard. Step one creates the client; step two assigns people. Remember the creator is already an Account Manager on it.

const client = await api.post('/companies', { name, industry, website });
await api.post(`/companies/${client.id}/members`,
               { userId: designerId, roles: ['DESIGNER', 'COPYWRITER'] });
invalidate(['companies']);              // refresh switcher + filter list
4

Rename a client

Send only name. Any extra key is a 400. Update the client switcher, the dashboard filter label and any open breadcrumb from the response — the name appears in many places.

const updated = await api.patch(`/companies/${id}`, { name });
invalidate(['companies', ['dashboard']]);
5

Assign a client to a user

Pick an existing employee, tick every role they will hold on this client, post the list. Exclude current members from the picker so you never send a duplicate.

const employees = await api.get('/users');
const members = await api.get(`/companies/${id}/members`);
const assignable = employees.filter(
  e => !members.some(m => m.userId === e.id && m.status === 'ACTIVE'));

await api.post(`/companies/${id}/members`, { userId, roles });

// adding a hat later means sending the whole set, not just the new one
await api.patch(`/companies/${id}/members/${membershipId}`,
                { roles: [...member.roles, 'ACCOUNT_MANAGER'] });
6

Promote someone to Admin — Super Admin only

Render the control only for a Super Admin, disable it on their own row, and confirm before sending. Handle the two guard-rail errors with clear copy rather than a generic failure toast.

if (!isSuperAdmin(me.platformRole)) return null;      // never render

await api.patch(`/users/${userId}/platform-role`,
                { platformRole: 'AGENCY_ADMIN' });
7

Handle a role that changed mid-session

A demoted Admin keeps a token that still claims the old role until it is re-issued, so the UI can offer an action the API now refuses. Centralise this in your API client: on any 403 from an admin route, refresh the session once, and if the role really did change, re-render from the new role instead of showing an error.

if (res.status === 403 && !retried) {
  const { user } = await api.post('/auth/refresh');    // re-issues the token
  setSession(user);
  if (!isAdmin(user.platformRole)) return redirect('/');
  return retryOnce();
}

Before you call it done

  • An AGENCY_ADMIN account sees the dashboard, every widget, and all client data — including clients they are not a member of.
  • An AGENCY_ADMIN sees no role control, no delete-client action and no health strip.
  • A USER account cannot reach any admin route, by menu or by typing the URL.
  • Delete requires typing the client name, reports what it removed, and clears the client from every cache and the switcher.
  • Every request body contains only documented keys — no stray fields.
  • A 403 anywhere in the admin area re-reads the session instead of showing a dead end.
  • Filters live in the URL; reloading a filtered dashboard restores the same view.

One open question

GET /api/admin/system/health is written as Super Admin only. If the Product Owner decides Admin should see platform health too, the only frontend change is dropping the isSuperAdmin check around that one widget.
