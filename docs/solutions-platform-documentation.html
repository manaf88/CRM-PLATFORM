Part I

The system today

Nineteen modules and roughly sixty endpoints are built and working. The difficult foundations — multi-client isolation, role enforcement, and the approval state machine — are real implementations, not scaffolding. The weaknesses are in the connective tissue between features, and in the operational pieces needed to run in production.

1What the platform is

Solutions is the system itself. It is not a record in the database. The records are the clients Solutions works for — Al Zaman, Curby, Taxero.

An employee works across several clients, holds a possibly different role on each, and sees only the clients they are assigned to. The interface therefore reads Solutions (Curby): Solutions is the product, the client is the workspace currently in view.

Business language mapped to the data model
Business termIn the codeMeaning
Solutions—The application. No table, no endpoint
ClientcompanyAl Zaman, Curby, Taxero — one row each
EmployeeuserA member of Solutions staff
"Dina works on Curby as Designer"company_membershipLinks an employee to a client, carrying the role
The clients I work onGET /companiesReturns only that employee's clients

Naming note

The API calls a client a company, and every feature route is scoped /api/companies/{companyId}/…. The interface says "client". This split is deliberate for now — renaming the routes is a large refactor and the permission rules are still settling — but it should be unified once they are final.

Data isolation

Every feature route carries a companyId, and two guards run on it. CompanyAccessGuard confirms the caller has an active membership for that client; CompanyRolesGuard then confirms their role on that client permits the action. An employee on Curby cannot read Taxero data by changing the URL. This is the property the whole system depends on and it should be re-verified after any change to routing or guards.

Two read permissions to review

5The content approval workflow

The most intricate logic in the system, and the piece most worth protecting with tests. Transitions are enforced server-side; any move not listed here is rejected.

Permitted transitions
ActionAllowed fromResults inWho may act
Submit to client DRAFT · IN_INTERNAL_REVIEW · CHANGES_REQUESTED · APPROVED READY_FOR_CLIENT Account Manager, Social Media Manager
Approve READY_FOR_CLIENT · CHANGES_REQUESTED APPROVED Client Owner, Client Reviewer, Account Manager
Request changes READY_FOR_CLIENT · APPROVED CHANGES_REQUESTED Client Owner, Client Reviewer, Account Manager
Reject READY_FOR_CLIENT · CHANGES_REQUESTED · APPROVED CANCELED Client Owner, Client Reviewer, Account Manager
Publish URL required APPROVED · SCHEDULED PUBLISHED Account Manager, Social Media Manager

Requesting changes also fires the automation engine, which can create fix-up tasks for the copywriter and designer. Every transition writes to the post's approval log with actor, timestamp and note, and notifies the roles that need to know.

The gap in this flow

SCHEDULED is a valid status and posts carry a scheduledAt date, but no scheduler exists in the codebase. Nothing fires when that time arrives. Publishing means posting on the platform by hand and pasting the resulting URL back in — the system records publication, it does not perform it.

Conventions

  • Passwords must be at least 12 characters wherever one is set.
  • Undeclared fields in a request body produce a 400 — send only documented fields.
  • Rate limits: 5/min on login, 20/min on refresh, 100/min elsewhere.
  • Enum values are exact strings; anything outside the documented set is a 400.
  • There is no registration endpoint. Accounts are created by administrators, or by accepting an invitation.

7Known gaps

Stated plainly, because these determine what can be tested and what can be deployed.

Gaps, by consequence
GapBlocksDetail
No email of any kindTesting Nothing in the codebase sends mail. Invitation tokens are returned in an API response and must be carried to the recipient by hand. Admin-created employees receive a temporary password the same way
Invitation link path mismatchTesting The API returns /auth/accept-invitation?token=… while the frontend route is /accept-invitation, so generated invite links reach the 404 page. One line, on either side
No database migrationsProduction Schema is created by TypeORM synchronize, which is enabled only in development. A production deployment would start against an empty database with no way to create its tables
No schedulerFeatures No cron or job runner exists. Scheduled publishing, follow-up reminders and overdue alerts are therefore impossible today
Essentially no testsConfidence Only the default framework example files. The approval state machine and the client isolation guards — the two places a bug is most costly — are unprotected
Audit module is emptyAccountability The folder exists with no code. Per-post and per-task histories do exist, but there is no system-wide audit trail
No pagination on postsScale Leads, tasks, campaigns, notifications and responsibilities all accept a limit. Posts do not, and will degrade once a client has a year of content
Redis required but unusedHygiene REDIS_HOST is a required environment variable and the container runs, but no code uses it and no Redis client is even installed. It will refuse to start without a service it never contacts

One silver lining

Because Redis is already provisioned and running, the infrastructure needed for scheduled jobs, distributed locks and background queues is in place. It simply has not been used yet.

Part II

What we do next

The system has not been tested end to end, and the reason is structural rather than a matter of effort: onboarding a person requires hand-carrying a secret, and the daily flow asks people to type in work the system already knows about. This part diagnoses that, then sets out a plan in priority order.

8Why the flow feels wrong

1

Nobody can get into the system

Invitations return a token in an API response, so an administrator must copy it out of a dialog and send it over a messaging app — and the resulting link is broken anyway. There is no email anywhere in the codebase. This single gap blocks testing the approval workflow, because approvals require a client contact who currently cannot be onboarded.

2

It is a set of forms, not a workflow

Creating a content plan does not create posts. Creating a post does not create tasks for the designer and the copywriter. Every step re-enters information the system already holds. That is the source of the "bad flow" feeling: staff feed the database instead of the database feeding them work.

3

There is no "what do I do today"

An employee signs in and arrives at a dashboard rather than at their work. Nothing assembles my tasks, posts awaiting my action, and leads due for follow-up across the clients that person works on. The API shape prevents it: every route is scoped to one client, so the question cannot even be asked.

4

Clients must use an internal tool

To approve one post, the contact at Al Zaman needs an account, an invitation, a password, and then has to navigate an agency dashboard built for staff. That friction is the usual reason client approvals stall.

5

"Scheduled" does not schedule

A post can be given a date and moved to SCHEDULED, but no job ever runs. The system is entirely passive: it never tells anyone that something is due, overdue, or waiting on them.

6

The responsibility matrix is decorative

This is the feature closest to the original goal — rules and responsibility per employee — and nothing reads it. Recording that "Dina manages Instagram content" changes no behaviour anywhere in the system. The structural reason is that responsibility areas have no link to work items, so nothing can be routed by them.

9The plan, by priority

P0 — Before anything can be tested

1

Replace passwords-in-transit with activation links

Rather than bolting email onto the current design, collapse the two onboarding paths into one. An administrator creates an employee with no password at all; the invited client contact follows the same route. Both receive one email containing a "set your password" link. The token machinery already exists in the invitations module and only needs generalising.

Use SMTP through the existing Solutions mailbox — no third-party service required. When SMTP is not configured, write the activation link to the log, so development and testing never block on mail delivery again.

Effort 1–2 days · Unlocks all end-to-end testing

2

Fix the invitation link path

Align the path the API returns with the route the frontend registers.

Effort minutes · Unlocks the entire approval workflow

3

Write a demo seed script

Two clients, six employees with mixed roles, a month of posts spread across every status, twenty leads, and a set of open tasks. A flow cannot be judged against an empty database, and hand-entering test data is precisely why testing keeps being postponed.

Effort 1 day · Unlocks meaningful review sessions

P1 — Turn it into a system

4

A cross-client "my work" endpoint

Introduce a /api/me/… namespace that is not scoped to a single client — the one architectural change on this list. GET /api/me/work returns, grouped by client and ordered by urgency: tasks assigned to me with overdue first; posts awaiting my action, resolved from my role on each client; leads whose follow-up date has arrived; and unread notifications.

This becomes the landing page and is the largest single improvement in how the product feels. Staff open the application and see their day rather than a menu.

Effort 1–2 days · Unlocks the home screen for everything after

5

Generate work automatically, through the existing engine

Do not hard-code "a post creates tasks". The automation module already stores per-client trigger-and-action rules with a free-form config column; it simply has only two triggers. Add POST_CREATED → CREATE_CONTENT_TASKS, CONTENT_PLAN_APPROVED → CREATE_POSTS_FROM_PLAN and POST_APPROVED → CREATE_PUBLISHING_TASK.

The rule config holds the template — for a reel, a script task for the copywriter and an edit task for the designer, each due a set number of days before the scheduled date. Keeping this in rules rather than in code matters because clients differ: one may require client review on every post, another may not.

Effort 2 days · Unlocks the system generating work instead of receiving it

6

Make the responsibility matrix operational

Add an optional responsibility-area reference to posts and tasks. That one field turns the matrix from a chart into a routing table.

Matrix recordsSystem behaviour
TO_WORK_ONReceives the auto-created task, replacing role-based guesswork
TO_APPROVEReceives the approval request — not everyone holding the role
TO_SUPERVISE · TO_BE_HELD_RESPONSIBLENotified when work in that area runs late
TO_BE_INFORMEDReceives a digest of changes in that area
TO_CONSULTSuggested when a task is blocked or questioned

Then surface it where the work is — showing "Instagram content — Dina manages, Amir approves" on the post itself. The matrix currently lives on a page nobody opens; placed beside the work it becomes the answer to "who owns this?"

Effort 2–3 days · Unlocks the original goal, actually operating

7

Public client review links

A revocable, expiring tokenised URL that shows a post — title, caption, images via presigned links — and accepts approve or request-changes with a name and a note, without any account. It writes into the same approval log, attributed as "via review link", so the audit trail stays whole.

Extend the same mechanism to a whole content plan, so a client can approve a month in one sitting. That is what agencies actually want, and it is the version clients will praise.

Trade-off: weaker identity than a login. Mitigate with expiry, revocation, and binding the link to the invited email address.

Effort 2–3 days · Unlocks approvals that do not depend on client software adoption

P2 — Before production

8

Database migrations

Non-negotiable. Today a production deployment creates no tables at all.

Effort 1 day · Unlocks deployment

9

Tests on the two costly areas

The approval state machine and client data isolation. Everything else can be caught by hand; a silent isolation failure cannot.

Effort 2 days · Unlocks changing code without fear

10

Housekeeping

Pagination on posts; either use Redis or stop requiring it; fill in the audit module; settle the two broad read permissions noted in section 3.

Effort 1–2 days

P3 — Leverage, once the loop works

11

A scheduler, in two stages

Now: a job every few minutes that reads the clock and nudges — an approved post whose date has arrived notifies the social media manager and creates a publishing task; a lead due for follow-up notifies its owner; an overdue task notifies the assignee and their supervisor from the matrix. This changes the system's character from passive to proactive without touching a single social platform. It is also where the idle Redis earns its place, providing the lock that stops jobs firing twice across instances.

Later: real publishing through the Meta and LinkedIn APIs — per-client authorisation, token refresh, media upload and platform-specific rules. Substantial work that should not block anything above it.

Stage one 1 day · Stage two weeks

12

Further candidates

A content calendar as a month grid, which is the view agencies live in. Workload per employee across clients, using data already held. Recurring tasks for retainer work. Design file versioning, so revisions are traceable. A client-facing dashboard. Real AI generation, by switching the provider that is already integrated.

ARunning the system

# 1 — Infrastructure, from solutions-platform/
docker compose up -d postgres redis minio

# 2 — API, from solutions-platform/api/
npm ci
npm run start:dev          # listens on port 3000, prefix /api

# 3 — Frontend
npm ci
npm run dev                # http://localhost:5173

The API will not start while MinIO is unavailable, because it verifies its storage bucket during boot. It also refuses to start without REDIS_HOST, despite never contacting Redis.

The first administrator is created on boot from BOOTSTRAP_ADMIN_EMAIL and BOOTSTRAP_ADMIN_PASSWORD. This is required because there is no public sign-up: without it, no one could sign in and no one could create anyone. The step is idempotent — it creates the account when missing, promotes it if it exists without administrator rights, and never overwrites an existing password.
