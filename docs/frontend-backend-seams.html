Reads with the approval flow guide

The task approval contract dated 19 September stands unchanged — approver, submit / approve / request-changes, the per-client queue, the error codes. This document adds to it. Where the two disagree, this one is newer: section 7 here replaces "not in this release" there.

0The four questions, answered

#QuestionAnswer
A Can every role upload files? Now yes, for every internal role. It was Account Manager, Designer and Social Media Manager only — Copywriter and Sales Agent have been added, because a copywriter attaches a brief and a sales agent attaches what a lead sent them. Client roles cannot upload: they read attachments on posts, they do not add them. The per-file limit is now 25MB (was 20).
B Backfill approvers on old IN_REVIEW tasks? No. Nobody agreed to approve work submitted before there was anything to agree to. They stay approverId: null; admins name approvers by hand. Your "Needs an approver" tile is the right behaviour, and the dashboard counts them (internalApprovalWithoutApprover).
C Is the task comment shape stable? Yes. { id, companyId, taskId, userId, comment, createdAt }. user is never embedded today. If that changes it will be additive — keep your normaliser.
D Should clients receive DRAFT posts? No, and the backend now enforces it. A member whose only roles are CLIENT_OWNER / CLIENT_REVIEWER no longer sees DRAFT or IN_INTERNAL_REVIEW posts in the list, and asking for one by id answers 404 — not 403, which would confirm it exists. Anybody holding an agency role, and platform admins, see everything as before.

3Ageing reminders and the daily digest

typeGoes toWhen
REVIEW_WAITING_24Hthe approver24h after submittedForReviewAt, still IN_REVIEW
REVIEW_WAITING_48Hevery Account Manager on that client48h after, still IN_REVIEW
 
{
  "type": "REVIEW_WAITING_24H",
  "title": "A review has been waiting a day",
  "message": "Jessika's \"Taxero — May carousel\" has waited a day for your review",
  "entityType": "TASK", "entityId": "<taskId>",
  "metadata": { "submittedForReviewAt": "…", "approverId": "…", "waitingHours": 26 }
}

A sweep runs every 15 minutes. Exactly one notice per task per threshold per round — re-submitting after changes re-stamps the clock, so the task can earn a fresh 24h notice next round. Approving, requesting changes or cancelling clears the clock, and nothing further fires.

The email digest

One email per person per day at 08:00 in the agency timezone (DIGEST_HOUR, DASHBOARD_TIMEZONE), and only to people with something waiting: a review sitting on them, one of their own tasks sent back in the last 24 hours, or — for client users — a post that has been READY_FOR_CLIENT for more than 48 hours. Nothing waiting, nothing sent. A muted type is left out of the email too, and emailDigest: false turns it off entirely.

SMTP is optional, and unset today

With no SMTP_HOST configured the API writes each email to the log instead of sending it and carries on. That keeps password reset and the digest working end to end on staging — the reset link is in the log — but no real email leaves the server until SMTP is configured: SMTP_HOST, SMTP_PORT, SMTP_SECURE, SMTP_USER, SMTP_PASSWORD, MAIL_FROM.

4Forgot and reset password

POST/api/auth/forgot-passwordnew

No session · 5 requests per minute · Always 200

{ "email": "jessika@agency.com" }

// 200 { "success": true } — whether or not that address has an account.
// The endpoint never says which, so it cannot be used to find out who works here.

POST/api/auth/reset-passwordnew

No session · 10 requests per minute

{ "token": "<from the emailed link>", "password": "a new password" }

// 200 { "success": true }
// 400 for a token that is wrong, already used, or older than an hour:
{ "statusCode": 400, "message": "This reset link is no longer valid. Ask for a new one." }

The email links to <FRONTEND_URL>/forgot-password?token=…. Tokens are single-use, valid one hour, stored hashed. A successful reset signs the account out everywhere.

Minimum password length is 12, not 8

Creating a user, accepting an invitation and the bootstrap admin all require twelve characters. A reset that accepted eight would be the short way round all three. Please raise the frontend rule to 12 — or say the word and we drop every rule to 8 together.

5Public report links

Who: Account Manager, or any admin

// 201 — a link was minted. This is the only time the URL is ever shown.
{ "url": "https://app…/r/<token>", "created": true,
  "expiresAt": "2026-12-26T…", "createdAt": "2026-09-27T…" }

// 201 — a link already exists. No URL: only its hash is stored.
{ "url": null, "created": false, "expiresAt": "…", "createdAt": "…" }

// POST …/share?rotate=true — replaces it, revoking the old link.

Why a second POST does not hand back the same URL

The ticket asked for the token to be stored hashed and for a repeat POST to return the existing link. Those cannot both be true — a hash cannot be turned back into a URL. Hashing won, because a leaked database row must not open a client's reports. So: the first POST gives you the URL, a repeat POST tells you one exists, and ?rotate=true mints a new one and kills the old. Suggested UI: "A public link already exists (expires 26 Dec). Replace it?"

6Lead outcomes

PATCH/api/companies/:companyId/leads/:leadId/statusextended

{ "status": "LOST", "lostReason": "PRICE", "note": "Went with a cheaper agency" }
{ "status": "WON",  "dealValue": 4500.00 }

// 400 when the field does not match the status:
//   "lostReason can only be set when the lead is moved to LOST"
//   "dealValue can only be set when the lead is moved to WON"

lostReason is one of PRICE, TIMING, WENT_ELSEWHERE, NO_RESPONSE, NOT_A_FIT, OTHER. Both fields are returned on the lead, and both are cleared when the lead leaves that status — a lead that stops being lost stops having a reason, so the reports never count yesterday's answer.

The [Reason] prefix on the note can go: the reason is a real field now.

7Post stage chaining

Built to the decisions in the handoff, not to section 7 of the original approval ticket: the order is a gate on submitting, and the post never moves on its own.

ChangeBehaviour
Task.sequence Integer, nullable, 1–50. Accepted on POST /tasks and PATCH /tasks/:id. Only meaningful with relatedEntityType: "POST" — otherwise 422 SEQUENCE_NEEDS_POST. Two tasks on one post may not share a number — 409 SEQUENCE_TAKEN, with the id of the task that holds it.
Submitting 409 PREVIOUS_STAGE_OPEN while any task on the same post with a lower sequence is not DONE or CANCELED. Body carries openTaskIds. Starting work is not blocked — people prepare in parallel.
The post gate POST /posts/:id/submit-review answers 409 STAGES_OPEN with openTaskIds and the full stages object while any staged task is still open. A post with no staged tasks behaves exactly as today.
Read model GET /posts/:id gains stages. 
// on GET /api/companies/:companyId/posts/:postId
"stages": {
  "total": 2,
  "done": 1,
  "open": [
    { "taskId": "…", "title": "Design the carousel", "sequence": 2, "status": "IN_PROGRESS" }
  ]
}

// 409 on submitting stage two too early
{ "statusCode": 409, "error": "Conflict",
  "code": "PREVIOUS_STAGE_OPEN",
  "message": "An earlier stage on this post is still open: Write the copy",
  "from": "IN_PROGRESS", "action": "submit-for-review",
  "openTaskIds": ["copy-task-id"] }

done + open.length === total always: a cancelled stage is counted in none of the three, so a progress bar built from these reaches the end instead of sticking at "1 of 2". stages is on the single-post read only — the list would need a query per row.

The task attachment response changed shape

The three task attachment paths are unchanged, but they are served by the new code and return the object above instead of the old { id, companyId, taskId, fileId, createdAt }. Old rows were copied across, so nothing is lost — but the task attachment list needs the new type.

Attaching while creating

The record does not exist yet when somebody picks files in a create modal, so: upload each file on selection, then send the ids with the create.

// POST /tasks, /posts, /campaigns, /leads all accept
{ …, "attachmentFileIds": ["file-a", "file-b"] }   // max 20

// The record and its attachments are written in one transaction: a create
// that fails validation leaves zero attachment rows behind.

Rules

RuleDetail
Who can listAnyone who can read the parent. Posts only for client users — never leads, campaigns, tasks or the brand profile.
Who can addThe roles that edit that parent (posts: AM, SMM, designer, copywriter · leads: AM, sales agent · campaigns: AM, SMM · brand profile: AM, designer · tasks: any internal role).
Who can deleteThe person who attached it, an Account Manager on that client, or a platform admin — otherwise 403. Answers 204.
Limits25MB per file → 422 FILE_TOO_LARGE · 20 attachments per record → 422 ATTACHMENT_LIMIT.
TypesImages, PDF, Office documents, CSV/text, MP4/MOV, ZIP. Anything else is refused at upload. Executables are not on the list.
The same file twiceAttaching a file that is already on that record returns the existing row rather than a duplicate.
Deleting the file itselfThe file leaves storage only when the last thing pointing at it lets go — a file on a task and its post survives either one being removed.
Abandoned uploadsSwept nightly at 03:30: files older than 24 hours with no references are deleted and the count logged.

Activity log rows ATTACHMENT_ADDED / ATTACHMENT_REMOVED are written for tasks, which is the only one of the five with an activity log. Posts, leads and campaigns have none to write to — tell us if that matters and it becomes its own small ticket.

9What is deliberately not here

  • post_review_gates — the separate multi-gate ticket. It solves the same problem as section 7 by a different route: gates stored on the post, rather than tasks with a sequence. Building both would give the platform two internal review machines. Section 7 is what the frontend is built against, so that is what shipped. Say the word if the gate table is still wanted and we will reconcile them properly.
  • The post moving itself to READY_FOR_CLIENT, and the INTERNAL_REVIEW_COMPLETED approval log row from the original ticket. The handoff replaced both: a person presses submit, the backend only decides whether to allow the press.
  • Swagger. The project still has no OpenAPI setup. This document and the 19 September one are the contract.
  • End-to-end tests. The new logic is covered by unit tests (66 across 9 suites); there is still no e2e harness in the repo.
